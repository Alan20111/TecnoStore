1. Descripción del negocio y problema

TecnoStore es una cadena de tres tiendas de tecnología (Centro, Polanco y Satélite) que vende celulares, laptops, computadoras, tabletas, relojes, audífonos y accesorios, nuevos y reacondicionados, y tiene un taller que repara equipos de clientes.

Hoy el negocio lleva el inventario, las ventas y el taller en hojas de cálculo separadas. Eso provoca: ventas de piezas que ya no hay, equipos con número de serie que no se sabe a quién se vendieron, garantías que nadie registra, órdenes de taller que "se pierden" entre estados, descuentos sin control y ningún rastro de quién cambió un precio. El sistema resuelve esos problemas con una base de datos que protege la integridad por sí misma (constraints, transacciones, triggers y roles) y una aplicación de escritorio para el personal.

Decisión clave del modelo: los equipos con número de serie se controlan pieza por pieza (UnidadSerie); los accesorios y refacciones se controlan por cantidad (Producto.stock_actual). Producto.requiere_serie distingue ambos casos.

2. Objetivo general y alcance

Objetivo: diseñar y desarrollar un sistema de escritorio que administre ventas, compras, inventario, taller, clientes, proveedores y usuarios de TecnoStore, con una base de datos en SQL Server que aplique las reglas del negocio, soporte procesos transaccionales, limite accesos por rol, registre los cambios sensibles y dé información para decidir.

6. DER y relaciones

Relaciones importantes

1. Venta → DetalleVenta → UnidadSerie → Garantia. Cada venta tiene una o más líneas. Si el producto requiere serie, cada línea apunta a una pieza física (id_unidad), y de esa línea nace su garantía (relación 1:1 con UNIQUE en id_detalle_venta). Así se sabe exactamente qué número de serie se llevó cada cliente y hasta cuándo está cubierto.

2. Compra → DetalleCompra → UnidadSerie. Las piezas entran por compra; UnidadSerie.id_detalle_compra dice de qué compra y proveedor viene cada pieza. Admite NULL para equipos usados que entraron de un cliente y se reacondicionaron.

3. OrdenServicio → DetalleOrdenServicio (TipoServicio o Producto) → HistorialEstadoOrden. Cada línea de la orden es mano de obra o refacción (un CHECK obliga a que tenga al menos una de las dos), y cada cambio de estado queda en el historial con el usuario.

Relaciones muchos-a-muchos

ProductoProveedor (un producto lo surten varios proveedores y un proveedor surte muchos productos, con el costo de cada uno), UsuarioRol (usuarios y roles) y EmpleadoTipoServicio (qué servicios puede hacer cada técnico; la usa fn_TecnicoHabilitado para impedir que se asigne una reparación de placa a quien no está capacitado).

9. Seguridad y matriz de permisos

La seguridad existe dentro de SQL Server, no solo en la aplicación. Se crearon 4 roles de base de datos con permisos diferenciados y usuarios de prueba asociados a cada rol. La aplicación puede conectarse con el login de cada perfil (ModoConexion = Roles en App.config), de modo que aunque alguien quitara una validación del código, SQL Server seguiría negando lo que el rol no tiene.

ProductosCRUDR + guardar y ajustar (SP)RR

Se usan GRANT (lectura del esquema, ejecución de procedimientos), DENY (tablas de seguridad, auditoría, reporte de utilidad para el operador, escritura en catálogos) y REVOKE (se retira un permiso dado por error). Ningún usuario operativo tiene db_owner. La demostración con EXECUTE AS USER / REVERT está al final de 07_Seguridad.sql. El detalle de permisos reales está en MatrizPermisos.pdf.

La interfaz sigue a la base de datos. Al iniciar sesión la app ejecuta usp_PermisosApp: toma el rol del usuario, se pone en el lugar de su usuario de base de datos con EXECUTE AS USER y pregunta con HAS_PERMS_BY_NAME si tiene cada permiso. Con esas 15 capacidades (ver costos, registrar venta, cancelar venta, ajustar inventario…) se muestran u ocultan módulos del menú, botones, paneles y columnas de costo. Si cambia un GRANT o DENY, la interfaz cambia sola; y aunque alguien llame la operación, SQL Server la rechaza. Las pruebas P33 y P34 comprueban la matriz del Operador y del Supervisor.

Menos información por pantalla. Siguiendo divulgación progresiva (NN/g), las leyes de Hick y Miller y el diseño de dashboards de Stephen Few: tablas de 5 a 7 columnas, búsqueda con 2 o 3 filtros y el resto en «Más filtros», un solo botón principal por pantalla, Dashboard de 4 indicadores, sin gráficas de pastel y sin nombres técnicos en la interfaz. Detalle y fuentes en GuiaDiseno.md §4.

Además, las contraseñas de la aplicación se guardan como HASHBYTES('SHA2_256'), nunca en texto plano; tras 5 intentos fallidos el usuario se bloquea y solo un Administrador lo reactiva.

11. Transacciones y manejo de errores

Los procesos que modifican varias tablas usan el mismo patrón: SET XACT_ABORT ON, validaciones con THROW, BEGIN TRY / BEGIN TRANSACTION / COMMIT y en el BEGIN CATCH un ROLLBACK seguido de THROW para que la aplicación reciba el mensaje. SCOPE_IDENTITY() obtiene el id del encabezado recién insertado.

¿Por qué hace falta la transacción en la venta? Si se guardara el detalle pero fallara el descuento de stock, quedaría una venta cobrada con inventario falso; si la pieza quedara "Vendida" sin garantía, el cliente perdería su cobertura. Con la transacción o pasa todo o no pasa nada. La demostración con caso exitoso y fallido de los cuatro procesos está en 11_Transacciones.sql y su salida real en 04_Evidencias/salidas_sql/11_Transacciones.txt.

ACID

Atomicidad: la venta se guarda completa o no se guarda. Consistencia: al terminar se cumplen todas las constraints (stock ≥ 0, precio ≥ costo, totales cuadrados). Aislamiento: otra caja no ve una venta a medias. Durabilidad: tras el COMMIT la venta sobrevive a un apagón (log de transacciones).

Los procedimientos usan el nivel por defecto READ COMMITTED (sin lecturas sucias) y bloquean con UPDLOCK, HOLDLOCK solo las filas que importan (stock del producto y último folio), para que dos cajas no vendan la última pieza ni generen el mismo folio, sin bloquear toda la tabla como haría SERIALIZABLE. Al elegir pieza se usa READPAST para saltar piezas que otra caja tiene apartadas.

Solución de Visual Studio 03_WindowsForms/TecnoStore.sln, C# con .NET Framework 4.8 (incluido en Windows 10/11; usa System.Data.SqlClient sin paquetes extra). Organización:

CarpetaContenido

App.configCadenas de conexión (única o una por rol) y modo de conexión.

Acceso a datos. La clase Db centraliza la cadena de conexión (App.config), abre cada conexión con using y le pasa a SQL Server el usuario de la app con sp_set_session_context (lo usan los triggers de auditoría y el historial). Todo el SQL usa SqlParameter con tipo; ningún texto del usuario se concatena. Los formularios no contienen SQL: llaman a los repositorios. Las excepciones se atrapan con try/catch y los mensajes de THROW se muestran en un MessageBox.

Experiencia de usuario. DataGridView para listados y detalles, ComboBox para toda llave foránea (nunca se escriben IDs), DateTimePicker para fechas, NumericUpDown para cantidades y precios, ErrorProvider y fondo rojo para campos obligatorios, MessageBox para confirmar operaciones críticas, estados de lectura/edición con Nuevo, Editar, Guardar, Cancelar y Eliminar, y el botón Guardar se desactiva mientras se procesa para evitar doble ejecución. Las tablas se refrescan después de cada operación.

Consumo de la base: 16 procedimientos, 5 vistas (vw_ProductosActivos, vw_VentaCompleta, vw_OrdenServicioCompleta, vw_StockBajo, vw_TopProductos) y funciones en consultas (fn_TotalCompradoCliente, fn_ClasificacionCliente, fn_TotalOrden, fn_VentasPorCategoria).

15. Conclusiones y mejoras futuras

El proyecto muestra la diferencia entre almacenar datos y construir una solución de información: la base no confía en la aplicación. Las constraints impiden datos imposibles, las transacciones evitan información a medias, los roles limitan lo que cada perfil puede hacer aunque se salte la interfaz, los triggers dejan rastro de los cambios sensibles y las vistas, funciones y reportes convierten los movimientos en información para decidir (qué resurtir, qué se vende, quién vende, cuánto deja cada categoría).

Mejoras futuras: facturación electrónica (CFDI) para clientes con RFC; cierre de caja diario; traspasos de inventario entre sucursales; notificación al cliente cuando su equipo está listo; respaldo automático programado con restauración de prueba; dashboard con gráficas en la aplicación; y uso de async/await en las consultas largas para que la interfaz no se congele.
